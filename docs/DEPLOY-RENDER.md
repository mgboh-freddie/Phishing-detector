# Deploying to Render

## Before you start: the free-tier catch

Render's free plan has an **ephemeral filesystem**. The SQLite database holds
your API keys and all scan history, and on the free plan it is **wiped on
every deploy, restart, and spin-down**.

That means the key you gave your friend stops working, without warning,
the first time the service restarts. For a service whose whole point is
handing someone a key, that is usually a dealbreaker.

Three ways to deal with it:

1. **Attach a disk** (needs a paid instance, from $7/month). In `render.yaml`
   set `plan: starter`, add the `disk:` block that's commented in there, and
   set `DB_PATH=/var/data/api.db`. This is the straightforward fix.
2. **Accept it** and recreate keys after each restart. Fine while you are
   only demoing to yourself.
3. **Seed a key from an environment variable.** The app supports this
   directly: set `BOOTSTRAP_API_KEY` and it creates that key at startup,
   every startup, on any plan. Because the key lives in Render's env
   config rather than the filesystem, it survives every deploy, restart,
   and spin-down -- the free tier's persistence problem, solved without
   a paid disk.

   Generate a strong key locally:

   ```bash
   python -c "import secrets; print(secrets.token_urlsafe(32))"
   ```

   Set `BOOTSTRAP_API_KEY` to that value in the Render dashboard (it's
   already declared in `render.yaml` with `sync: false`, so Render
   prompts for it and never stores it in the repo). Optionally set
   `BOOTSTRAP_API_KEY_NAME` too, to label the key something other than
   `bootstrap` in `python -m api.keys list`.

   The app refuses to start if the key is shorter than 24 characters --
   a weak key on a public API is worse than no key. Hand your friend the
   plaintext you generated the way you'd hand over a password, since
   that's what it is. If it ever leaks, revoke it (`python -m api.keys
   revoke <key_id>`, run locally against a copy of the database if you
   have no shell) -- a revoked bootstrap key stays revoked, it is never
   recreated by a later restart.

The free plan also **spins down after 15 minutes idle**. The first request
after that waits for the container to start plus ~2.4s to load the model, so
expect roughly a minute. Requests after that are fast.

Memory is fine: measured at **~280 MB** with the model loaded and serving,
against the free plan's 512 MB.

## Steps

**1. Push this repo to GitHub.**

```bash
git remote add origin https://github.com/<you>/Phishing-detector.git
git push -u origin main
```

Render deploys the `main` branch as configured. Private repos work — you just
authorise Render's GitHub app for them.

**2. In Render: New → Blueprint**, select the repo. It reads `render.yaml`.

**3. Set `DASHBOARD_PASSWORD`** in the Render dashboard when prompted. It is
marked `sync: false` precisely so it never lives in the repo. `SECRET_KEY` is
generated by Render automatically — you don't set it and shouldn't.

**4. Deploy**, then check it:

```bash
curl https://<your-service>.onrender.com/v1/health
```

You want `{"status":"ok","model_loaded":true,...}`.

**5. Create a key.** Render's Shell tab (paid plans) gives you:

```bash
python -m api.keys create --name "friend-name" --rate-limit 120
```

On the free plan there is no shell, so use option 3 above instead: generate a
key locally, set it as `BOOTSTRAP_API_KEY` in the Render dashboard, and
redeploy. The app seeds it on startup and it survives every restart.

## Why native Python and not the Dockerfile

There is a working `Dockerfile` in this repo, but `render.yaml` uses Render's
native Python runtime instead. Two reasons:

- **The Dockerfile has never been built.** Docker Desktop wouldn't start on
  the development machine, so it has only ever been read, not run.
- **It runs as a non-root user (uid 1000).** Render mounts persistent disks
  in a way that collides with that, and SQLite in WAL mode needs to create
  `-wal`/`-shm` files *in* the data directory, not just write one file.

If you'd rather use Docker, switch `runtime: python` to `runtime: docker` —
but expect to debug the disk permissions, and build the image locally first.

## Python version

`.python-version` pins 3.12.10. **Do not drop below 3.11.** The model bundle
is pickled with scikit-learn 1.8.0, which publishes no wheels for 3.10 —
on 3.10 pip resolves to 1.7.2 and every model load warns that results may be
invalid.

Send your friend `docs/HANDOVER.md` and a key. Read that file first — it
